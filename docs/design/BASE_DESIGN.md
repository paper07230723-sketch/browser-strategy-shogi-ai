将棋AIブラウザプロジェクト 基本設計書
更新日：2026年11月19日
文書の位置付け：プロジェクト全体の目的・構成・設計原則を定義する基本設計
1. プロジェクトの目的
ブラウザ上で動作する将棋AIを開発する。主な利用環境はiPhone Safariとし、Googleアプリ内ブラウザおよびChromeでも利用できることを目指す。

最終目標は、通常の強い将棋AIとして対局できる性能を保ちながら、利用者が指定した戦型・戦略を自然に目指すAIを実現すること。

戦型指定はエンジンの評価関数そのものを改造するのではなく、エンジンが提示する合法手・候補手を戦略レイヤーで評価し、候補の選択に反映させる。
2. 開発上の前提
- 開発者はコーディングに不慣れなため、作業手順は実行場所・対象ファイル・コマンドを明示し、可能な限りコピーして実行できる形で提示する。
- 正常動作している既存機能を不用意に変更しない。
- 実際のファイル、Gitの状態、ログを確認してから変更方針を決める。
- 一度に複数の原因候補を変更せず、小さな変更単位で検証する。
- 安定性を新機能の追加より優先する。
3. 開発の優先順位
現時点の優先順位は次のとおり。
1. iPhone Safariでの安定動作を維持する。
2. Googleアプリ内ブラウザ／Chromeでの動作を維持する。
3. 直前の着手を盤面上で色分けするUI改善を行う。
4. 戦法指定なしの通常対局と右四間飛車の戦略レイヤーを整備する。
5. 右四間飛車の実戦テストを行い、戦略評価を調整する。
6. 追加戦法を検討する。
機能追加と安定性が衝突する場合は、安定性を優先する。
4. 技術・構成方針
過去のブラウザ将棋AIをそのまま土台にするのではなく、将棋メイトおよび usumerican/yaneuraou-suisho-petite を参考資料として扱う。参考にするのは主に構成・設計上の考え方であり、コードを無条件にコピーしない。

アプリケーションは責務を分離し、概ね次の領域を独立させる。
- UI：盤面、操作、設定、状態表示
- 盤面・対局状態：局面、手番、合法手、対局進行
- エンジン通信：USIプロトコル、コマンド、応答解析
- Worker：重い探索処理とメインUIの分離
- 戦略レイヤー：戦型の形成度、候補手の戦略的評価
- 棋譜：USI/KIF等の入出力
- 設定：エンジン、強さ、思考時間、戦型など
- テスト：各責務の単体・結合テスト
ディレクトリ構成は src/、`public/`、`test/` などに分割し、Vite/Vitest相当の開発・テスト環境を基本とする。既存リポジトリの実際の構成を優先し、設計書に合わせるためだけの大規模な移動は行わない。
5. 参照プロジェクトとライセンス
主な参考先：
- 将棋メイト：https://github.com/usumerican/shogimate
- YaneuraOu Suisho Petite：https://github.com/usumerican/yaneuraou-suisho-petite
YaneuraOuおよび関連コードにはGPL-3.0等のライセンス条件が関係する。コードの流用、改変、配布、依存ライブラリの追加を行う際は、各リポジトリ・ファイルのライセンスと配布義務を確認する。アーキテクチャを参考にすることと、コードを複製することを区別する。
6. エンジン設計
現在扱うエンジンは以下の3種類。
- 水匠
- つようら王11mini
- つようら王11micro
各エンジンは同一の対局UI・対局管理から利用できるようにする。エンジン固有の初期化・USI通信・探索停止・リソース解放などは共通インターフェースの背後に隔離する。

評価関数そのものは変更しない。戦型指定はエンジンの評価値・候補手・読み筋を利用し、アプリ側の戦略レイヤーで実現する。
7. WASM・Worker・ブラウザ要件
- UIはエンジン初期化の完了を待たずに先に表示する。
- WASMの初期化と探索は非同期で行い、可能な限りWorkerに分離する。
- SIMD等の実行環境機能は必要に応じて検出し、利用可否に応じた経路を選ぶ。
- SharedArrayBuffer が必要な構成では、Cross-Origin Isolationを有効にする。
- 配信環境では必要なCOOP/COEPレスポンスヘッダーを正しく設定する。
- ブラウザ差異を前提にし、実機で検証する。SafariだけでなくGoogleアプリ内ブラウザ／Chromeの動作も確認対象とする。
- エラー表示は利用者に分かる内容にし、`[object Event]` のような情報量のない文字列を表示しない。
- 原因調査に必要な初期化・USI・エラー情報は残す。診断目的だけの一時コードは検証終了後に整理する。
8. エンジンの状態管理
エンジン状態は少なくとも以下を区別する。
- loading：初期化中
- ready：対局・探索可能
- thinking：探索中
- error：初期化または通信に失敗
エラー後の再初期化・復旧を検討する。状態遷移とUI操作の可否を一致させ、探索中や停止応答待ちに重複した初期化・対局開始を行わない。
9. UIの基本機能
基本画面に必要な機能は次のとおり。
- 将棋盤・駒の表示と操作
- 人間対AIの対局
- 先手／後手の選択
- エンジン選択
- 思考時間・強さの設定
- 評価値表示
- 戦型選択（当初は「戦法指定なし」「右四間飛車」）
- 待った、投了、新規対局
- 棋譜の保存・読み込み
- 初期化中・探索中・エラー等の状態表示
実装済み機能の詳細は HANDOVER.md を正とする。基本設計書は機能の方向性を定義し、実装済みかどうかを逐一管理する文書ではない。
10. AIの強さと時間
強さ設定は初期案としてLv1/Lv2/Lv3などの複数段階を設ける。ただし、段階名だけで具体的な棋力を保証しない。実際の強さはエンジン設定・探索条件・実戦テストに基づいて調整する。

思考時間は0〜5秒程度を基本範囲とする。0秒は探索を無効にする意味ではなく、最短の探索条件を指定する意味とする。設定可能範囲は実装と端末性能に合わせて調整する。
11. 戦法指定なしモード
「戦法指定なし」では、通常のエンジン評価を優先する。戦略スコアを加算せず、候補手は原則MultiPV=1とする。戦法指定なしモードの挙動を、戦型指定モードのために変更しない。
12. 右四間飛車モードの基本方針
最初に実装する戦型指定は右四間飛車とする。固定の手順を強制するのではなく、目標とする駒組み・攻撃筋を示し、局面に応じて柔軟に形成する。
- 先手側の目標形：▲4六歩、▲4七銀、▲4八飛
- 後手側の目標形：△6四歩、△6三銀、△6二飛
- 先手の主な攻撃筋：4筋
- 後手の主な攻撃筋：6筋
これらは目標条件であって、固定された指し手順や必須の完全一致局面ではない。相手の対応や局面に応じて、駒組みの順番・攻撃開始時期を柔軟にする。
13. 右四間飛車の戦略評価
エンジンの評価と戦略評価を分け、概念上は次の値を管理する。
- engineScore：エンジン本来の局面評価
- strategyScore：右四間飛車の戦略目的への適合度
- finalScore：候補手の最終比較に使う評価
strategyScore は少なくとも次の観点から構成する。
1. 駒組み進行度（0〜3）：目標の歩・銀・飛車の配置がどの程度整っているか。
2. 攻撃への貢献度（−2〜+2）：攻撃駒・支援駒の配置、攻撃経路の確保など。
3. 攻撃成立可能性（−2〜+2）：具体的な仕掛けの有無、攻撃の継続性、相手の反撃など。独自の深い探索を追加するのではなく、短いエンジンPV等を補助情報として利用する。
4. 主導権（−2〜+2）：相手に応手を強いるか、守備駒を拘束するか、相手の攻めを制限するか、攻撃筋を切り替えられるか。
各スコアの重み・閾値・候補数は固定せず、実戦テストと端末負荷を見て調整する。
14. 攻撃の継続性と柔軟性
単に攻撃筋に駒を置いたことだけを高く評価しない。例えば、▲4五歩から▲4五銀、▲4五飛のように攻撃が継続・発展する見込みを評価する。相手に止められ、その後の攻めが続かない手は高評価にしない。

4筋への攻撃に固執せず、局面によって他の筋の方が有効なら攻撃筋を切り替えられるようにする。ただし、攻撃筋切り替えを単純な固定ルールとして強制しない。候補手の比較から自然に判断できる構成を目指す。

相手が主攻撃筋に守備駒を集中させた場合、それは突破しにくくなる要因である一方、守備駒を拘束し他の筋を弱くする可能性もある。守備集中を一律に失敗と評価しない。
15. MultiPVと候補手比較
- 戦法指定なし：原則MultiPV=1。
- 右四間飛車：初期案はMultiPV約3。iPhone Safariの負荷・応答性を確認して調整する。
エンジンは合法手・候補手・評価・PV等を提供する。戦略レイヤーは候補手ごとの駒組み進行度、攻撃への貢献、攻撃成立可能性、主導権を比較する。エンジンを独自の探索エンジンで置き換えない。
16. 局面に応じた重みの調整
将来的には、序盤の駒組み中、攻撃準備、戦いの開始後、攻撃が停滞した局面などで戦略スコアの重みを変えることを検討する。初期実装で複雑化しすぎず、実戦で必要性が確認された場合に追加する。
17. 今後追加する可能性のある戦法
将来的な候補は以下。ただし右四間飛車が十分に動作・検証できるまでは実装しない。
- 鬼殺し／新鬼殺し
- 嬉野流
- 村田システム
新戦法の追加を理由に、最初の右四間飛車の実装範囲を不必要に広げない。
18. 棋譜・局面の扱い
対局状態と棋譜を一貫して管理する。保存・復元後も局面、手番、棋譜、選択中のエンジンや戦型設定が矛盾しないことを重視する。USI形式の棋譜を利用する箇所では、通常の指し手と駒打ちを区別して処理する。
19. テスト方針
少なくとも次の領域を確認する。
- 盤面の描画・座標変換
- 合法手・駒移動・成り・駒打ち
- 手番・局面状態の更新
- USIコマンド・応答解析
- エンジン初期化・探索開始・停止
- エンジン切り替えとリソース解放
- 棋譜保存・読み込み・復元
- 評価値の符号・表示
- 戦略評価と候補手選択
- iPhone Safari、Googleアプリ内ブラウザ、Chromeでの実機動作
20. 開発フェーズ
1. ブラウザ基盤・エンジン初期化の安定化
2. 戦法指定なしの通常対局
3. 右四間飛車の戦略レイヤー
4. 実戦テスト・戦略評価の調整
5. 必要性が確認できた戦法・機能の追加
各フェーズは実際のリポジトリ状態と HANDOVER.md の進捗を照合して進める。
21. 初期段階で避けること
- 右四間飛車の検証前に複数の戦法を同時実装する。
- 固定の手順・囲い・駒組みを強制する。
- 戦略レイヤーのために独自の深い探索エンジンを作る。
- 評価関数やエンジン本体を不用意に改造する。
- 根拠のない多数のパラメータを導入する。
- Safariで動作しているWASM初期化経路を、必要性を確認せず大きく変更する。
22. 完成の考え方
右四間飛車の初期完成条件は、先手・後手の両方で目標形を柔軟に形成し、先手4筋／後手6筋を主軸に自然な攻撃を行い、攻撃継続性や他筋への切り替えも局面に応じて判断できること。通常モードでは戦略スコアの影響を受けず、従来のエンジン対局を維持する。

プロジェクト全体の当面の完成条件には、SafariとGoogle／Chromeでの起動・対局安定性、および既存機能の退行がないことを含める。
